# Track A — Harness reality-check

> De-risks: spec §6.2 (opencode driven by Workflows), §6.3 (delegation via MCP tool), §11.1 (primitive mapping). **Highest architectural risk.**

## Question

Does the core execution model hold in practice?
1. Can `opencode serve` + `@opencode-ai/sdk` run **headless in a container**, driven programmatically, with **LSP diagnostics fed back for self-correction**?
2. Is the **`subagent_type` hardcoding limitation** (§6.2) still real in the current opencode release, or has it been fixed — and does that change whether we need the MCP delegation shim (§6.3)?
3. Does **Render Workflows** actually deliver the semantics the spec assumes: DAG-shaped chaining, parallel fan-out, per-task isolated containers, scale-to-zero, retries + timeouts up to 24h?

## Why it's load-bearing

The entire architecture ("Workflows owns the DAG; opencode is a dumb per-node worker; delegation happens via an MCP tool that returns a handle, never blocks") is a *workaround* for opencode's limitations plus a *bet* on Workflows' capabilities. If opencode's limitation is gone, §6.3 may be unnecessary. If Workflows can't do 24h tasks / fan-out / scale-to-zero as described, the Render platform mapping (§11) needs rework.

## Sources to review

- opencode (SST) repo + docs — server mode, `@opencode-ai/sdk`, agent config (`opencode.json`, `.opencode/agents/*.md`), `Task` tool `subagent_type` behavior in the **latest** version.
- Render Workflows docs — task model, chaining/fan-out, container lifecycle, timeouts, retries, scale-to-zero.
- Render MCP + CLI + API docs (self-provisioning, §11.1).
- **Local:** `agent-workflows-template/` (`render.yaml` + `src/`), `render-agents/`, `render-agent-harness/`, `render-agent-library/`.

## Findings

_Verified July 2026. opencode latest release **v1.17.19** (published 2026-07-13). Render Workflows is in **beta/Early Access**. Repo has moved to `anomalyco/opencode` (formerly `sst/opencode`)._

### Q1 — Headless opencode + SDK + LSP self-correction: **CONFIRMED**

- `opencode serve` runs a headless HTTP server exposing an **OpenAPI 3.1** spec (`/doc`), default `127.0.0.1:4096`, `--port`/`--hostname`/`--cors` flags; protect with `OPENCODE_SERVER_PASSWORD` (HTTP basic auth). Docs: https://opencode.ai/docs/server/ and https://opencode.ai/docs/cli/.
- The **`@opencode-ai/sdk`** package is a type-safe client generated from that OpenAPI spec. `createOpencode()` boots server + client; `createOpencodeClient({ baseUrl })` attaches to an already-running server. Session lifecycle is `client.session.create()` → `client.session.prompt({ path:{id}, body:{ parts:[…] } })`. Config can be passed inline or picked up from `opencode.json`. Docs: https://opencode.ai/docs/sdk/. This is exactly the "one opencode instance per Workflow task container, driven by the SDK" model in §6.2/§11.1 — no blocker.
- **LSP diagnostics fed back for self-correction: real and current, but OFF by default.** opencode spawns LSP servers and feeds compiler diagnostics into the next agent turn after each edit; this is a genuine differentiator in 2026 (Claude Code / Codex don't do it by default). Docs: https://opencode.ai/docs/lsp/. **Two caveats the spec doesn't note:** (a) LSP is **disabled by default** — you must set `lsp: true` (or configure servers) in `opencode.json`; (b) opencode's own docs recommend, for many projects, running `lint`/`typecheck` **CLI** tools instead of LSP (servers drift, eat memory, slow the loop) and documenting those commands in `AGENTS.md`/skills. **Implication:** the spec should treat "compiler feedback for self-correction" as the invariant and allow **either** LSP **or** a typecheck/test CLI in the agent loop — don't hard-bind to LSP. (The §8.2 plan to *also* harvest LSP `references`/`callHierarchy`/`documentSymbol` for graph edges is separate and still fine, but likewise requires LSP explicitly enabled.)

### Q2 — `subagent_type` hardcoding: **SPEC CLAIM IS NOW STALE / FALSE in current opencode**

- The spec (§6.2) says "current opencode versions hardcode the Task tool's `subagent_type` to the built-ins (`explore`, `general`)." **In v1.17.19 this is not true.** Verified directly against source at tag `v1.17.19` (`packages/opencode/src/tool/task.ts`): the parameter is a **free-form string**, not an enum —
  `subagent_type: Schema.String.annotate({ description: "The type of specialized agent to use for this task" })`.
  (Older `sst/opencode` `task.ts` used `z.string()` for the same field — it was **never a literal enum in the tool schema**; the enum described in issue #20059 was the model-facing *description* listing built-ins, not a type constraint.)
- The Task tool **dynamically** builds its list of invocable agents at runtime from `Agent.list()` filtered to `mode !== "primary"`, then further filtered by the caller's `permission.task` glob rules. Custom subagents defined in `opencode.json` / `.opencode/agents/*.md` with `mode: "subagent"` **are** resolvable by name via `subagent_type`. Docs confirm: `permission.task` glob control, `hidden: true` for "internal subagents that should only be invoked programmatically by other agents via the Task tool," and `@`-mention manual invocation. Docs: https://opencode.ai/docs/agents/. A commenter on the feature request reproduced `task({ subagent_type: "coder-fast" })` correctly routing to a custom agent/model. Issue #20059: https://github.com/anomalyco/opencode/issues/20059.
- **Additionally**, v1.17.x has moved *past* the limitation the spec assumes: (i) **subagent→subagent delegation** is supported (PR #7756) gated by a per-agent `task_budget` + `permission.task` rules to prevent runaway recursion; (ii) the Task tool now supports **`task_id`** (resume/continue a prior subagent session) and an experimental **`background`** mode (`OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true`) that launches a subagent async and notifies on completion. PR #7756: https://github.com/anomalyco/opencode/pull/7756.
- **Real, current footguns (caveats, not the old limitation):**
  - Subagents defined as **mode files under a `modes/` dir** get force-set to `mode: "primary"` by `ConfigAgent.loadMode()`, which then *excludes* them from the Task tool's dynamic list. **Workaround: define subagents in `opencode.json` (and/or `.opencode/agents/*.md`), not in `modes/`.** Issue #28879: https://github.com/anomalyco/opencode/issues/28879; related #29616: https://github.com/anomalyco/opencode/issues/29616.
  - A custom subagent whose `model` isn't in the provider's explicit `models` array can fail with a **bare `Error`** (swallowed `ProviderModelNotFoundError`). **Workaround: declare every subagent model explicitly in `opencode.json` providers.** Issue #31179: https://github.com/anomalyco/opencode/issues/31179.
  - **`@mention` is non-deterministic** — it injects a *suggestion* into the primary's prompt, not a hard spawn; the primary may handle inline instead of spawning a subagent session. So for programmatic delegation, drive the **Task tool / SDK**, never `@mention`. Issue #19538: https://github.com/anomalyco/opencode/issues/19538.
- **Consequence for §6.3:** the MCP-delegation shim's stated justification — *"sidesteps the `subagent_type` limitation entirely"* — is **obsolete**. That is no longer why you'd build it. **However, the shim is still the right design for the *other* (and actually load-bearing) reason stated in §6.2:** opencode subagents are **ephemeral child sessions in a single process** — not durable, not distributed across containers, not 24h-safe, no cross-container retry/state. Cross-slice orchestration must stay in Workflows. So: **keep §6.3, but re-motivate it around durability/distribution/24h, and delete the `subagent_type`-limitation rationale from §6.2/§6.3.** In-session native delegation (Implementer fanning out `@explore` or a custom `search` subagent within one slice) is now *more* capable than the spec assumed and can be used freely for bounded work.

### Q3 — Render Workflows semantics: **MOSTLY CONFIRMED, with two important stale/beta caveats**

Confirmed from https://render.com/docs/workflows and the launch post https://render.com/blog/durability-as-code-introducing-render-workflows:
- **Per-task isolated on-demand containers + scale-to-zero:** "Render automatically spins up a separate instance for each task run and deprovisions instances as runs complete… scales to zero when all runs finish." Spin-up "within seconds." ✅ (Note: docs say "within seconds," not the spec's "<1s" in §11.1 — soften that claim.)
- **DAG-shaped chaining + parallel fan-out:** tasks are functions; you chain by calling one task's function from another, and fan out with parallel calls (`Promise.all` over `.task()`). Confirmed by the official `blog-thumbnails-workflows` example (parent `generateThumbnails` fans out one isolated `generateThumbnail` subtask per model). ✅
- **Retries + timeouts up to 24h:** per-task `retry: { maxRetries, waitDurationMs, backoffScaling }`, `timeoutSeconds` "configurable up to 24 hours," per-task `plan` up to Pro Ultra (8 CPU / 32 GB). ✅
- **Managed queue + concurrency budget:** Render manages queuing at no extra cost; when at the workspace's max concurrent runs, new runs queue until capacity frees. Max concurrency is a paid, raisable limit — directly relevant to §13's "cost/concurrency budgeting for large fan-outs." ✅
- ⚠️ **STALE / beta caveat 1 — Blueprints cannot create or manage Workflow services.** Render docs (Workflows beta limitations) state verbatim: *"Blueprints do not yet support creating or managing workflows."* Corroborated by **both** local repos: `render-agents/render.yaml` ("Render Blueprints CANNOT create/manage Workflow services yet … must be created MANUALLY in the Dashboard") and `render-agent-harness` (`kind: workflows` marked *"Not Blueprintable yet"*). **This directly contradicts spec §11.2** ("Repo ships a root `render.yaml` … declaring … a Workflow service (orchestrators + agents)") and undercuts the headline **"single `render.yaml` Blueprint, one-click fork→deploy→run"** goal. Today the Workflow service must be created manually (New → Workflow) or via the **Render CLI/API**; the Blueprint can only provision the web control-plane, Postgres, Key Value, and crons.
- ⚠️ **Beta caveat 2 — other current limitations:** Workflows is **beta/Early Access**; tasks are **TypeScript/Python only** (fine — spec is TS/Py); **no native run scheduling** (use a cron to trigger); **network-isolated environments** can't have workflow runs talk to other services over private network; **no HIPAA hosts**. Source: https://render.com/docs/workflows.

### Local repo patterns worth reusing

**None of the four local repos use opencode** — they each implement their own LLM loop / agent runtime and wrap it on Render Workflows. They're still highly reusable as the *Workflows harness skeleton*; opencode slots in as the per-task worker.

- **`agent-workflows-template/`** — the best M0/M0.5 skeleton. Gateway (Hono web) + Workflow service (`src/workflow.ts`) + Postgres, all in `render.yaml` (web+db only — no Workflow service block, consistent with the Blueprint limitation). **Auto-wiring by convention** (drop a folder in `src/workflows|tools|skills/` → registered by name). **Markdown agents** (frontmatter: `model` tier, `tools`, `skills`, `token_budget`) wrapped as Render tasks by `loadAgents()`. Declarative `task({ name, timeoutSeconds, retry:{…} })`. **Tree-of-tasks** model: deterministic steps in-process, agent steps as isolated task containers, sequential or parallel fan-in. Local dev via `RENDER_USE_LOCAL_DEV=true` (in-process) and `render workflows dev` (true per-task containers). **Trace UI** (React) over a `/runs` + `/runs/:id/spans` API backed by Postgres — a ready-made model for the §11 dashboard + `AgentRun`/`TaskRun` data model (§12).
- **`render-agents/` (examples/demo)** — the closest analog to code-migrator: a real **issue→PR** and **PR-review fan-out** multi-agent pipeline on Workflows. Directly validates §6.3's design: the gateway **triggers the workflow root via the Render task API and returns immediately** (webhook can't block; "issue-to-pr can exceed GitHub's ~10s webhook timeout"), and the Workflow service itself triggers the reviewer fan-out as isolated `agent@standard` tasks — i.e. **trigger-returns-a-handle, Workflows-authoritative**, exactly §6.3. Also ships **operational patterns the spec omits**: a **stranded-run reaper** cron (fails roots orphaned by a lost task) and a **retention cleanup** cron; workflow **slug pinned in code**; both gateway and Workflow service need `RENDER_API_KEY` to `startTask`. Git clone/build/test happens in a `standard`-plan task container. Strong template for §9/§7.2 durability + the reaper as a DAG watchdog.
- **`render-agent-library/`** — the cleanest pattern for "one agent definition, three execution modes": `defineAgent(...)` → `.run()` (in-process, cheap/local), `.task()` (durable isolated Workflows subtask), `.stream()`. `registerAgentTasks([...])` wires `.task()` to Workflows once at module load; **`Promise.all` over `.task()` is the fan-out**; `.task()` falls back to in-process locally so the same code runs in dev. Also: `subagents: [agent]` (agents-as-tools delegation), `defineTool` with **SSRF-guarded `fetch`**, `defineMcpSource` for MCP servers, `SKILL.md` via a built-in `load_skill` tool, JSON-Schema structured output → `result.data`. If opencode-per-task ever proves too heavy for a role, this library is a viable lighter-weight worker for non-coding roles (Researcher/Planner) while opencode stays the coding worker (Implementer/Validator).
- **`render-agent-harness/`** — declarative **`render-harness.yaml` → generated `render.yaml`** (`pnpm build:bp`, `build:check` for CI staleness) with **capability packs** (bundled tools + MCP servers + skills + env schema). Runtimes: `web` / `cron` / `worker` / `workflows` (the last explicitly **"Not Blueprintable yet"**). Useful pattern for §11.2's "prompt for secrets via `sync:false`/`envSchema`" and for keeping the template's generated Blueprint in sync — but note it too confirms the Workflow-Blueprint gap.

## Recommendation

1. **Proceed with the core execution model — it holds.** Headless `opencode serve` + `@opencode-ai/sdk` per Workflow-task container, driven programmatically, with compiler-diagnostic self-correction, is real in v1.17.19. Do the **M0.5 running spike** (below) before committing deeper.
2. **Rewrite the §6.2 rationale.** Delete the `subagent_type`-is-hardcoded claim (false as of v1.17.19). Keep the architecture (Workflows owns the DAG; opencode is a per-node worker) but re-justify it solely on **durability, cross-container distribution, 24h runs, retries, and isolation** — the reasons that *are* still true.
3. **Keep §6.3 (MCP/native delegation tool), re-motivated.** It's still the right way to give a primary opencode agent Workflow-backed delegation ergonomics (return-a-handle, idempotent, role-scoped). Just stop citing the `subagent_type` limitation as its reason. Reuse the **`render-agents` gateway→task-API trigger** pattern verbatim.
4. **Fix the headline Blueprint claim (§11.2 / Goals).** The "single `render.yaml`, one-click fork→deploy→run" promise is **not fully achievable today**: Blueprints can't create/manage Workflow services. Options: (a) Blueprint provisions web+Postgres+KV+crons and the **control-plane bootstraps the Workflow service via Render CLI/API on first run** (self-provisioning already envisioned in §11.1 via Render MCP/CLI/API — lean into it); or (b) ship a two-step deploy (Blueprint + a documented "create Workflow service" step, as `render-agents` does). Track Render's roadmap for Blueprint-managed Workflows to reclaim true one-click.
5. **Treat "compiler feedback" as the invariant, not "LSP."** Enable opencode LSP explicitly (`lsp: true`) where it pays off (typed targets, plus §8.2 graph-edge harvest), but design the self-correction loop to also accept a `typecheck`/`test` CLI documented in `AGENTS.md`/skills — per opencode's own guidance.
6. **Bake in the operational patterns the spec skipped:** a stranded-run **reaper** cron (DAG watchdog), explicit **model declarations** for every opencode subagent, subagents defined in `opencode.json`/`.opencode/agents/*.md` (never `modes/`), and Task-tool/SDK-driven delegation (never `@mention`) for anything programmatic. Set per-agent `task_budget` if you use native subagent→subagent delegation for in-slice work.
7. **Soften two numeric claims in §11.1:** container spin-up is "within seconds," not "<1s"; and note the workspace **max-concurrency** cap (a paid, raisable limit) as a real constraint feeding §13's concurrency budgeting.
