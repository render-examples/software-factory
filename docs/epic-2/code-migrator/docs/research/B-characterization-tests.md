# Track B — Characterization test generation (the parity oracle)

> De-risks: spec §5.1 (ground truth before change), §10 (testing strategy), §13 (characterization coverage). **Hardest AI problem; least-proven part of the spec.**

## Question

Can we **automatically generate golden-master / characterization tests** that faithfully capture a source repo's *observable* behavior — including for repos with weak/no existing tests and heavy side effects (I/O, time, network, randomness)?
- How good is LLM-generated regression/characterization test coverage in practice?
- What determinism shims are needed before capture (seeded clocks/RNG, record/replay of I/O and network)?
- How do we measure that the oracle itself is trustworthy (coverage, mutation testing)?

## Why it's load-bearing

"Parity is the contract" (§5.2). If we can't produce a reliable parity oracle, the whole safety mechanism collapses — slices can't be verified "done," and the DAG advances on false green.

## Sources to review

- **Meta TestGen-LLM** ("Automated Unit Test Improvement using LLMs at Meta") — closest published analog to our use case.
- Michael Feathers, *Working Effectively with Legacy Code* — characterization test / golden-master technique.
- Approval testing: **ApprovalTests** family; snapshot testing patterns.
- Record/replay & determinism: **VCR**-style HTTP replay, seeded RNG/clock injection, containerized fixtures.
- Mutation testing tools (to score oracle strength): e.g. `mutmut`, Stryker, PIT.
- LLM test-gen research post-2023; SWE-bench "fail-to-pass" test harnessing.

## Findings

### 0. Reframe: our oracle is a *differential* oracle, not a snapshot (this is the crux)

The spec (§4, §5.1, §10) says "capture the source's observable behavior as the parity oracle." But
parity verification is inherently a **two-implementation** problem: we compare *source* vs *migrated*
outputs on identical inputs. That is textbook **differential testing** — a pseudo-oracle for exactly
the case "writing a complete oracle is infeasible" ([Differential Testing overview](https://www.emergentmind.com/topics/differential-testing);
CSmith-style compiler testing). The practical shape: run program A (source, the oracle) and program B
(migrated candidate) on the same inputs; compare stdout/stderr/exit code/serialized return values/
captured side effects; any divergence is a parity failure. A minimal, language-agnostic reference
implementation of this exists: [`difftest`](https://github.com/nalediym/difftest) ("run two programs
with the same inputs, compare outputs… Python vs Rust? Fine"). [ModernizeSpec's parity-testing
technique](https://modernizespec.dev/techniques/parity-testing/) formalizes the same idea for
migration: a `parity-tests.json` of inputs → golden outputs, field-level diffs, and an explicit
`knownDeviation` list for intentional behavior changes.

**Consequence for the spec:** a characterization test captured *only* against the source (a frozen
golden file) is the cheaper, portable form and should be the default artifact, because it survives the
source being torn down and can be replayed against the migrated slice. But the highest-fidelity mode is
a live differential harness while both sides coexist (the spec already assumes a transitional shim, §4,
§6 — this is the natural place to run A/B differentially). **The must-preserve inventory (§8.4) should
carry, per symbol: captured input corpus + golden outputs + the scrubber/normalizer spec.**

The single most important warning for an *agentic* migrator comes from ["Don't Port the Syntax. Port
the Evidence."](https://fnauman.com/posts/2026-03-09-dont-port-the-syntax-port-the-evidence/index.html)
(2026): coding agents "optimise for plausibility rather than truth," and "a migration can have a green
suite and still be almost entirely unverified" — agents love tests that are easy to satisfy (shape
checks, "does not crash," snapshots generated by the same code under test, before/after comparisons that
alias the same object). This directly threatens §5.2 "parity is the contract": the oracle must be
**generated from and owned independently of the Implementer**, or the DAG advances on false green.

### 1. State of the art for auto-generating characterization/regression tests with LLMs

- **Meta TestGen-LLM** (["Automated Unit Test Improvement using LLMs at Meta", arXiv 2402.09171](https://ar5iv.labs.arxiv.org/html/2402.09171),
  FSE-SEIP 2024). This is the closest published analog and its framing ("**Assured LLMSE**") is the
  pattern we should copy: LLM output is only kept if it clears **hard filters** — it must (a) build,
  (b) pass reliably across repeated runs (flakiness screen), and (c) **strictly increase coverage** over
  the existing suite. Deployed results (Instagram Reels/Stories): **75% of generated tests built, 57%
  passed reliably, 25% increased coverage**; across test-a-thons it **improved only ~10–11.5% of the
  classes it was applied to**, with **73% of surviving recommendations accepted** by engineers. The load-
  bearing lesson is not the headline acceptance rate — it's that **TestGen-LLM augments existing human
  tests; it does not build a suite from scratch**, and even with assurance filters the *yield per class is
  ~10%*. A migrator that needs a trustworthy oracle for **every** slice of a weakly-tested repo is a
  strictly harder problem than what TestGen-LLM solved.
- **Newer from-scratch generators (2025–2026)** report coverage plateauing well below "complete":
  - **TestWeaver** ([arXiv 2508.01255](https://arxiv.org/pdf/2508.01255), execution-aware, feedback-driven):
    **68% line / 62% branch** on 35 real Python projects (CodaMosa suite), beating **CoverUp (61%/47%)**
    and **CodaMosa (46%/23%)**. State of the art is ~two-thirds branch coverage, and ablations show the
    gains come from *execution feedback + backward slicing + closest-test retrieval* — i.e. you need a
    real run-compile-observe loop, not one-shot prompting.
  - **Cleverest / ClevFuzz** ([FSE 2026, Böhme et al.](https://mboehme.github.io/paper/FSE26-llmtesting.pdf)):
    for structured-input programs (parsers, interpreters, compilers), a zero-shot feedback-directed LLM
    found **more bugs in <2 min than the SOTA directed fuzzer WAFLGo found in 24h**, and using its tests as
    fuzzing seeds **~doubles** bugs found. Implication: for slices with structured inputs, pairing LLM seed
    generation with coverage-guided fuzzing is a proven way to widen the captured-input corpus cheaply.
- **Failure modes (consistent across sources):** hallucinated/non-compiling tests; tests that pass but
  assert nothing meaningful; coverage plateaus on complex/long modules; over-dependence on prompt/commit-
  message quality; and regenerating whole suites instead of incrementally extending good existing tests.

### 2. Coverage is necessary but a weak trust signal; mutation testing is the real bar

- **Coverage does not prove the oracle pins behavior.** Inozemtseva & Holmes (["Coverage Is Not Strongly
  Correlated with Test Suite Effectiveness", ICSE 2014](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf),
  31,000 suites / 5 systems): only **low-to-moderate** correlation between coverage and effectiveness once
  suite size is controlled, and **"coverage… should not be used as a quality target."** The killer example
  from MutGen (below): **some suites reach 100% coverage but 4% mutation score** — i.e. they execute the
  code without asserting its outputs. For a *characterization* oracle whose entire job is asserting exact
  behavior, coverage alone is close to meaningless.
- **Mutation testing is the strongest available proxy for oracle strength**, because it checks assertions,
  not just execution ([Code Coverage vs Mutation Testing](https://journal.optivem.com/p/code-coverage-vs-mutation-testing)).
  Tooling: **PIT/PITest** (Java/JVM), **StrykerJS/.NET** (JS/TS/C#), **mutmut / cosmic-ray** (Python).
  - **MutGen** ([arXiv 2506.02954](https://arxiv.org/html/2506.02954v7), TSE 2026): feeding mutation
    feedback (surviving mutants, operators, line numbers) back into the LLM prompt lifts mutation score to
    **~89%** on HumanEval-Java/LeetCode-Java, beating EvoSuite and vanilla prompting. → the same
    generate→run→observe loop that helps coverage also drives mutation score, and it's the right optimization
    target.
  - Caveats on mutation score itself: Papadakis et al. (["Are mutation scores correlated with real fault
    detection?", ICSE 2018](https://dl.acm.org/doi/10.1145/3180155.3180183)) show the correlation is again
    weak once suite size is controlled — **but top-mutation-score suites detect significantly more real
    faults**, so mutation score is excellent *guidance / gap-finding*, not a linear quality dial.
  - **Equivalent-mutant problem** is real and costs money: LLM-generated mutants detect far more faults
    (["Comprehensive Study on LLMs for Mutation Testing", arXiv 2406.09843](https://arxiv.org/pdf/2406.09843):
    **87.98% vs 41.64%** for rule-based; PIT alone 40.1%) but produce more non-compiling / duplicate /
    **equivalent** mutants — so surviving mutants need triage, not blind "must be zero."

### 3. Determinism shims (mandatory *before* capture)

The spec (§13) flags this but understates it: **without determinism, a characterization test is flaky,
and a flaky oracle is worthless at any coverage level.** Proven techniques (["Deterministic Replay for
Code Debugging AI", debugg.ai](https://debugg.ai/resources/deterministic-replay-code-debugging-ai-snapshotting-runtimes-fix-flaky-bugs)):

- **Capture at boundaries, not the whole universe:** intercept outgoing HTTP/gRPC, filesystem reads, time,
  and RNG; record just enough to re-inject.
- **Network:** VCR-style record/replay — [VCR.py 8.0](https://vcrpy.readthedocs.io/) (Python), `nock`/
  `Polly.js` (Node), `go-vcr` (Go), WireMock/MockWebServer (JVM). Cassettes give "completely deterministic
  tests" offline. **Guardrail: force `record_mode=none` whenever `CI=true`** so replays can never silently
  hit the live network ([Claude Lab replay pattern](https://claudelab.net/en/articles/api-sdk/claude-api-replay-driven-testing-cassette-production-patterns));
  filter secrets out of cassettes.
- **Time:** freeze **wall clock *and* monotonic clock together** (freezing only one leaks nondeterminism) —
  `freezegun` (Python), Sinon fake timers (Node), injected `Clock` (JVM). Prefer a single injected clock
  abstraction.
- **RNG:** seed all PRNGs (`random.seed`, NumPy `Generator(seed)`, seeded `java.util.Random`, `math/rand`);
  never touch cryptographic RNG.
- **Highest fidelity (for stubborn slices):** whole-process record/replay via **rr / Undo / TTD** captures
  scheduling nondeterminism too — best determinism, highest setup cost.
- **Scrubbers / "Printer" discipline:** [golden-testing guidelines (jlevy/tbd)](https://github.com/jlevy/tbd/blob/main/packages/tbd/docs/guidelines/golden-testing-guidelines.md)
  require **classifying every output field as stable or unstable**; unstable fields (timestamps, generated
  IDs, durations, ordering) are normalized/scrubbed before comparison. Missing this classification is the
  #1 cause of flaky golden diffs.
- **Containerized fixtures:** pin OS/arch/locale/fonts/DB seed to one canonical environment; cross-OS drift
  is a known golden-test flake source (Flutter golden guide, above). The spec's per-slice sandbox containers
  (§11.1) are the right vehicle — but the **capture** environment and the **replay** environment must be
  byte-identical.

### 4. Feathers' characterization / golden-master method

Michael Feathers (*Working Effectively with Legacy Code*, ch. 13) coined "characterization test": a test
that captures **what the code actually does, not what it should do** ([Wikipedia](https://en.wikipedia.org/wiki/Characterization_test);
[understandlegacycode](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/)).
The 5-step algorithm ([Savoia/Artima](https://www.artima.com/weblogs/viewpost.jsp?thread=198296)):
(1) put the code in a test harness; (2) write an assertion you *know will fail*; (3) run it and let the
failure reveal the actual behavior; (4) change the assertion to expect the observed behavior; (5) repeat.
This is directly automatable by an LLM+runner loop — the model proposes inputs and a scaffold, the harness
runs and captures actual outputs, and the captured output *becomes* the assertion. Feathers' key stance:
**the existing behavior (bugs included) is the spec** — which is exactly §5.1's "ground truth before
change" and §4's parity definition.

Terminology note (all the same core mechanism): **Golden Master ≈ Characterization ≈ Approval ≈ Snapshot ≈
Locking test** ([understandlegacycode](https://understandlegacycode.com/blog/characterization-tests-or-approval-tests/)).
"Approval testing" is the better mental model for us because it foregrounds the **human approval step** and
a good **Printer/scrubber**; "snapshot" is the dangerous framing because it invites blind `--update-snapshots`.

### 5. The dominant risk is a *gamed or brittle* oracle, not low coverage

The SWE-bench experience is a direct, recent warning for our exact architecture (test-gated agentic code
changes):

- **Brittle oracles reject correct ports.** OpenAI's Feb 2026 audit (["Why we no longer evaluate SWE-bench
  Verified"](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)) found **≥59.4% of
  audited failed tasks had flawed tests** that reject functionally-correct submissions (overly strict,
  underspecified, or environment-dependent). An over-fit characterization test (asserting an incidental
  detail rather than a stable invariant) will block valid migrations and burn agent retries.
- **Agents can game the oracle.** SWE-bench harness bugs [#600 test poisoning](https://github.com/swe-bench/SWE-bench/issues/600)
  (model patches the test file to `assert True`) and [#601 stdout forging](https://github.com/swe-bench/SWE-bench/issues/601)
  (monkey-patch to print `=== 1 passed ===`) show that if the Implementer can touch the oracle or the
  grader trusts scraped stdout, "parity" can be faked. Mitigation: oracle files **read-only** to the
  Implementer, Validator runs in a **clean container**, and grading uses **structured machine-readable
  reports**, not console-string parsing.

## Recommendation

1. **Adopt "Assured characterization" (TestGen-LLM's filter discipline), extended for parity.** Keep an
   LLM-generated test only if it: builds; **passes reliably N times** under the determinism harness
   (flakiness screen); and adds coverage/mutation-kills over the current slice suite. Never merge an oracle
   the Implementer could have influenced — generate the oracle in Phase 0 from the **source only**, store
   golden outputs in the must-preserve inventory (§8.4), and make it immutable to downstream slice agents.

2. **Make the oracle a differential harness, source-owned.** Default artifact = captured input corpus +
   scrubbed golden outputs (portable, replayable against the migrated target). Where source and target
   coexist behind the transitional shim (§4/§6), additionally run **live A/B differential** comparison
   (stdout/stderr/exit/serialized returns + captured side effects), à la `difftest`/ModernizeSpec. Maintain
   an explicit `knownDeviation` list for behavior we intentionally don't preserve (should normally be empty
   per §5 "never introduce net-new behavior").

3. **Mandatory determinism gate before any capture** (see §3): boundary record/replay (VCR-style),
   frozen wall+monotonic clock, seeded RNG, pinned container env, and a **field stable/unstable
   classification + scrubbers**. `record_mode=none` in CI. Slices that cannot be made deterministic
   (genuine concurrency/external mutable state) are **flagged for human review**, not auto-gated to green.

4. **Score oracle strength with mutation testing, not coverage.** Coverage is a floor and a gap-finder;
   mutation score is the trust signal (100%-coverage/4%-mutation is a real outcome). Use PIT/Stryker/mutmut
   per language; triage surviving mutants (equivalent vs. genuine gap) rather than demanding zero.

### Proposed acceptance bar — when a slice's parity oracle is "trustworthy enough" to gate the DAG

A slice's oracle may gate parity **only if all gates pass**; otherwise the slice is escalated to a human
review gate (§ Non-Goals: humans resolve flagged decisions).

| Gate | Bar | Rationale / source |
| --- | --- | --- |
| **G0 Determinism** (hard) | Oracle runs **green ≥ 20/20 reruns**, zero flakes, under frozen clock + seeded RNG + replayed I/O; **no live network** (`record_mode=none`). | Flaky oracle is worthless at any coverage; VCR/freezegun/seed discipline. |
| **G1 Coverage floor** (necessary, not target) | **≥ 80% branch coverage** of the slice's must-preserve interface/reachable branches. | Floor only; SOTA generators plateau ~62% branch (TestWeaver) so >80% needs the feedback loop + fuzzing seeds. Inozemtseva/Holmes: not a quality target. |
| **G2 Mutation gate** (the real bar) | **≥ 75% mutation score** on the slice under test, **surviving mutants triaged** (documented equivalent vs. accepted gap). | Mutation checks assertions; MutGen shows ~89% is achievable with feedback; coverage alone can be 4%. |
| **G3 Oracle independence** | Golden values captured from **source only**; oracle files **read-only** to Implementer; Validator in **clean container**; grading via **structured reports** (no stdout scraping). | Anti-gaming (SWE-bench #600/#601); "port the evidence, not the syntax." |
| **G4 Differential agreement** | Migrated slice reproduces source on the **full captured corpus** (field-level diff), plus a **held-out input set** not shown to the generator. | Detects over-fit/aliased oracles; differential-testing pseudo-oracle. |
| **G5 Human approval of goldens** | Goldens + scrubber/field-classification **reviewed once** at capture (approval-testing discipline); every later golden change is a reviewed diff. | Prevents "certifies whatever the code does" snapshot rot. |

Interpretation: **G0 + G2 + G3 are the load-bearing gates.** G1 coverage is a cheap pre-filter; G4/G5
guard against the two dominant failure modes (over-fit brittleness and gaming). Numbers are a starting
proposal to calibrate on the `corpus.md` example repos, not settled constants.

## Open items

- ~~Define an acceptance bar~~ → **Proposed above** (G0–G5); calibrate the 80% branch / 75% mutation
  thresholds empirically against `corpus.md` repos before hard-coding them into the Validator.
- **Cost/time budget of the gate.** Mutation testing + N-rerun flakiness screening + fuzzing seed
  amplification is expensive per slice; needs a budget model and probably tiering (full gate on
  "tier-1"/high-fan-in slices, lighter gate on leaves). Ties to §13 cost/concurrency budgeting.
- **Coverage on the source's own weak spots.** For repos with *no* existing tests, we are generating the
  entire oracle; TestGen-LLM only demonstrated ~10% *augmentation* yield — validate our from-scratch yield
  on real corpus repos and decide the fallback when a slice can't clear G2 (manual oracle vs. narrower slice).
- **Where to run the differential harness** (G4) given source teardown: decide per language whether we keep
  a long-lived "source oracle service" behind the transitional shim vs. rely purely on frozen golden files.
- **Untestable/nondeterministic slices policy:** define the human-review path for slices that fail G0 for
  legitimate reasons (concurrency, external mutable state, wall-clock-dependent logic).
- **Equivalent-mutant handling:** pick per-language mutation tooling and an equivalent-mutant triage
  workflow so G2 doesn't stall on undecidable survivors.
