## Final outcome (native pivot, 2026-07-17)

The spike first validated **opencode** end-to-end (headless port of `leven` with real `tsc` self-correction, events mapped into the `RunEvent` stream). But that same run showed the self-correction was just *"agent runs `tsc` in a shell tool and reads the error"* — which **render-agents' native engine already does** via the `workspace` tools. Combined with opencode's baggage (separate binary, blocking-prompt 5-min fetch timeout, opaque errors, second runtime + reconstructed observability), we **abandoned opencode** (`D-NATIVE`).

**Final validated implementation (native, on branch `spike/m0.5-opencode-runtime`):** a `migrator` markdown agent (native `DefaultRunner`, `tools: [workspace]`) + the `leven-migrate` workflow (clone → migrate → parity). Live run: workflow `status: completed`; the agent created `index.ts` + `tsconfig.json`, and the **parity oracle passed all four gates** — `index.ts` artifact, deps, `npx tsc --noEmit` (exit 0), behavior `npx ava` (**3/3**). typecheck + parity unit tests green.

Note on the parity oracle: behavior parity runs the **characterization tests (`npx ava`)**, not `npm test` — leven's `npm test` bundles `xo` (lint, not behavior; and its legacy eslint stack crashes under Node 24).

The opencode-specific hypotheses/notes below are retained for history but are no longer the chosen path.

## Live run result (2026-07-17)

Ran end-to-end against a real `sindresorhus/leven` clone using the real opencode runtime (opencode CLI 1.18.3, model `anthropic/claude-sonnet-4-6`, `ANTHROPIC_API_KEY` from `render-agents/.env`). Driven via `examples/demo/scripts/spike-debug.ts` (the real `SdkOpencodeDriver` + runner; a debug `RunContext` printed emitted events).

**Result: `run.completed`.** opencode headlessly explored the repo, installed TypeScript, wrote `index.ts` + `tsconfig.json`, hit a **real `tsc` error (`TS5108`) and self-corrected**, recompiled clean, regenerated `index.js`/`index.d.ts`, updated `package.json`, and passed smoke tests. Every step streamed through our mapper as `RunEvent`s (`run.started` → `message.assistant` → `tool.called`/`tool.result` for read/bash/write/edit/`file.edit`/todowrite → `run.completed`).

- **H1 (headless opencode + SDK):** ✅ validated live.
- **H2 (custom role-specific agent via `body.agent` + `opencode.json`):** ✅ ran as `leven-implementer` with env-substituted model.
- **H3 (compiler-feedback self-correction):** ✅ real `tsc` error caught and fixed (compiler feedback, per the "not LSP-specific" invariant; TS LSP server not installed in this env).
- **H4 (opencode events → render-agents event stream):** ✅ mapping proven via the runner's `ctx.emit`; the gateway persistence path (run creation + `run_events`) was separately confirmed. Full `/ui` visualization not yet screenshotted.
- **H5 (durable idempotent re-trigger):** ⏳ not exercised (wants Postgres); still gated.

**Gotcha found:** opencode returns a generic `500 UnknownError` (with only a log `ref`) when the model slug is invalid; the real cause (`ProviderModelNotFoundError`) only appears via `opencode run --print-logs --log-level DEBUG`. Use a catalog-valid slug (e.g. `anthropic/claude-sonnet-4-6`); set it via `OPENCODE_MODEL`.

**Not yet run live:** the full gateway workflow (`leven-migrate`) with the 4-gate parity oracle on a fresh clone + events in `/ui`, and H5. The `npm test` parity gate may surface `xo`/`ava`-on-TS tooling friction (a migration-tooling issue, separate from the harness).

## Purpose

Validate the foundational bets **empirically, before building the graph/slicing/parity layers on top**. This single spike de-risks:

- **`D-BASE`** — code-migrator builds on the `render-agents` codebase (durable orchestration + ops + event-sourced observability).
- **`D-OPENCODE`** — opencode is a pluggable *coding* runtime inside render-agents, used for coding roles.
- **Track A** — headless opencode + SDK + custom subagent via `subagent_type` + compiler-feedback self-correction.
- **Track G** — Render Workflows as per-task-durable plumbing; render-agents' durability layer (idempotency, reaper, fail-fast) carries over.

If the observability bridge or the coding-loop quality disappoints, we learn it now and fall back to the documented alternative (build a compiler-feedback loop into render-agents' own engine — single runtime).

## Hypotheses under test

1. **H1 — Headless drive.** `opencode serve` boots inside a render-agents `agent.task()` container and is drivable via `@opencode-ai/sdk` (session create → prompt).
2. **H2 — Custom subagent.** A role-specific subagent defined in `opencode.json` is invocable via the Task tool `subagent_type` (free-string resolution, v1.17.x), including the model-must-be-declared footgun.
3. **H3 — Self-correction.** A deliberate type/compile error triggers compiler/LSP diagnostics that flow back and the agent self-corrects — on a real repo (`leven`, JS→TS).
4. **H4 — Observability bridge (the decisive risk).** opencode's SSE event stream can be projected into render-agents' `run_events` log and shows up in the operator UI (`/ui`) with per-edit/per-tool granularity.
5. **H5 — Durability carryover.** The run is driven through render-agents' durable path (`agent.task()` → Render Workflows locally via `render workflows dev`), with idempotent re-trigger (deterministic child id) not spawning a duplicate.

## Steps

1. **Scaffold the base.** Stand up render-agents locally (`npm create render-agents` or run the existing repo); confirm gateway + Postgres + `/ui`, dispatch the sample workflow, watch it in the trace UI.
2. **Add an opencode runtime seam.** Introduce a `runtime: opencode` option on a markdown agent: the task container installs/boots `opencode serve` (password-protected), and a small adapter drives it with `@opencode-ai/sdk` (`createOpencodeClient({ baseUrl })` → `session.create` → `session.prompt`).
3. **Define a coding subagent.** In `opencode.json` (not `modes/` — forces `primary`), define an `implementer` subagent with an explicitly-declared model; enable `lsp: true` and/or a `typecheck` CLI. Invoke it via the Task tool `subagent_type: "implementer"`.
4. **Bridge events (H4).** Subscribe to opencode's event stream and project events into render-agents' `run_events` (map opencode sessions/messages/tool-calls → spans/messages). Verify in `/ui`.
5. **Self-correction run (H3).** Point it at a checked-out `leven`; task = "port `index.js` to TypeScript `index.ts` preserving behavior." Inject a deliberate type error (or let it make one); confirm diagnostics feed back and it self-corrects; run `leven`'s existing `ava` tests as the parity check.
6. **Durability check (H5).** Drive via `agent.task()` under `render workflows dev`; re-trigger with the same key; confirm no duplicate run and memoized output.
7. **Measure + write up.** Capture versions, cold-boot cost, event-bridge fidelity, and a go/no-go on `D-OPENCODE`.

## Out of scope (explicitly)
