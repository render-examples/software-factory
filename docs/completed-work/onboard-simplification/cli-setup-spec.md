# CLI Setup & Doctor Spec

Simplification item 4: reduce deployment to a guided setup + doctor command.

---

## Problem

Deploying render-factory today requires:

1. Fork the repository
2. Create a Render Blueprint from `render.yaml` (provisions gateway, Postgres, two cron jobs)
3. **Manually** create the Render Workflows service in the Dashboard (Blueprints can't provision Workflows)
4. Set `RENDER_WORKFLOW_SLUG` to match the service slug
5. Create a fine-grained GitHub PAT with Contents/PRs/Issues RW on the target repos
6. Create a GitHub webhook pointing at `https://<gateway>/channels/github` with a shared secret
7. Set `GITHUB_TOKEN`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_BOT_LOGIN`
8. Set `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`
9. Set `RENDER_API_KEY` and `RENDER_WORKSPACE_ID`
10. Optionally: create a Slack app, configure event subscriptions and interactivity URLs, set `SLACK_BOT_TOKEN` and `SLACK_SIGNING_SECRET`
11. Ensure the Workflows service has the same env vars as the gateway (DATABASE_URL, model key, GitHub token, Render API key, etc.)
12. Verify everything works

That's 10–12 steps with multiple context switches between the Render Dashboard, GitHub settings, and the terminal. A founder who misses one gets a silent failure or a cryptic error.

Vercel's equivalent is: click "Deploy," select a GitHub connector, type a repo name, done.

We can't match one-click deploy (Blueprints don't support Workflows), but we can make the multi-step process guided, validated, and recoverable.

---

## Proposal: two CLI commands

### `render-factory init`

An interactive guided setup that walks a founder through deploying the factory. It uses the Render API (via `RENDER_API_KEY`) to provision what it can, prompts for what it can't, and writes a `.env` file with everything it collects.

### `render-factory doctor`

A non-interactive diagnostic that checks every prerequisite and reports what's healthy, what's missing, and how to fix each issue. Run it after `init`, after a failed deploy, or any time something seems wrong.

## `render-factory init`

### Prerequisites

- Node.js 22+
- A Render API key (the command prompts for it if not set)
- A GitHub fine-grained PAT (the command prompts for it)

### Flow

### What `init` does programmatically

| Step | Method | Notes |
|------|--------|-------|
| Authenticate with Render | Render API `GET /owners` | Validates the API key and selects the workspace |
| Deploy Blueprint | Render API (or prompt to do it in Dashboard if API doesn't support Blueprint creation) | Provisions gateway, Postgres, crons |
| Find/verify Workflows service | Render API `GET /services` filtered by name | Can't create — prompts for manual creation |
| Validate LLM key | `POST` to provider's models endpoint | Anthropic: `GET /v1/models`; OpenAI: `GET /v1/models` |
| Validate GitHub token | GitHub API `GET /user` + `GET /installation/repositories` | Confirms identity and repo access |
| Generate webhook secret | `crypto.randomBytes(32).toString('hex')` | Stored in env var |
| Set env vars on services | Render API `PATCH /services/:id/env-vars` | Both gateway and Workflows service |
| Write local `.env` | Write file | For local dev with `docker compose` |

### What `init` does NOT do

- Create the Workflows service (can't — no API for it yet)
- Create the GitHub webhook (can't programmatically via fine-grained PAT — prints instructions instead)
- Create a Slack app (too many Dashboard steps — prints a link and instructions)
- Modify the codebase (no agent edits, no config generation beyond `.env`)

### Flags

| Flag | Effect |
|------|--------|
| `--slack` | Run only the Slack setup step (for adding Slack after initial setup) |
| `--github` | Run only the GitHub setup step (for adding repos after initial setup) |
| `--env-only` | Skip service creation; just collect credentials and write `.env` |
| `--non-interactive` | Fail instead of prompting; for CI or scripted setups. Reads from env vars or `--key=value` args |

## `render-factory doctor`

A diagnostic command that checks every prerequisite and prints a status report. Non-interactive, safe to run repeatedly, returns exit code 0 if healthy or 1 if any check fails.

### Checks

```
$ npx render-factory doctor

===========================

  ✓ RENDER_API_KEY is set and valid (workspace: acme-eng)
  ✓ Gateway service found: render-factory-gateway (running)
  ✓ Workflows service found: render-factory-workflows (running)
  ✓ Database found: render-factory-db (available)
  ✓ Gateway health check: https://render-factory-gateway-xxxx.onrender.com/health → 200

Environment variables (gateway)
  ✓ DATABASE_URL
  ✓ RENDER_FACTORY_API_KEY
  ✓ RENDER_FACTORY_ENCRYPTION_KEY
  ✓ RENDER_WORKFLOW_SLUG = render-factory-workflows
  ✓ ANTHROPIC_API_KEY
  ✓ GITHUB_TOKEN
  ✓ GITHUB_WEBHOOK_SECRET
  ✓ GITHUB_BOT_LOGIN

Environment variables (workflows)
  ✓ DATABASE_URL (matches gateway)
  ✓ ANTHROPIC_API_KEY (matches gateway)
  ✓ GITHUB_TOKEN (matches gateway)
  ✓ RENDER_WORKFLOW_SLUG (matches gateway)

LLM provider
  ✓ Anthropic API key valid (can list models)

  ✓ Token authenticated as "acme-bot"
  ✓ Token has access to: myorg/frontend, myorg/api, myorg/docs

  ✗ No webhook found on myorg/frontend pointing at the gateway
    → Add a webhook: URL https://render-factory-gateway-xxxx.onrender.com/channels/github
      Events: issues, issue_comment, pull_request, pull_request_review
      Secret: use the value in GITHUB_WEBHOOK_SECRET

  - SLACK_BOT_TOKEN not set (Slack is optional)
  - SLACK_SIGNING_SECRET not set

  ✓ Gateway last deployed 2h ago (commit abc1234)
  ✓ Workflows last deployed 2h ago (commit abc1234)

Summary: 18 passed, 1 failed, 2 skipped
  ✗ GitHub webhook not configured on myorg/frontend
```

### Full check list

| Category | Check | How |
|----------|-------|-----|
| **Render platform** | API key valid | `GET /owners` |
| | Gateway service exists and is running | `GET /services` by name, check status |
| | Workflows service exists and is running | `GET /services` by name, check status |
| | Database exists and is available | `GET /postgres` by name |
| | Gateway health endpoint reachable | `GET /health` on gateway URL |
| **Env vars (gateway)** | Each required var is set | `GET /services/:id/env-vars` |
| **Env vars (workflows)** | Each required var is set | `GET /services/:id/env-vars` |
| | Shared vars match between services | Compare `DATABASE_URL`, `ANTHROPIC_API_KEY`, `GITHUB_TOKEN`, `RENDER_WORKFLOW_SLUG` |
| **LLM provider** | API key works | Provider-specific model list call |
| **GitHub** | Token authenticates | `GET /user` |
| | Token has repo access | `GET /repos` or `GET /installation/repositories` |
| | Token has required permissions | Check `X-OAuth-Scopes` or fine-grained permission headers |
| | Webhook exists on each accessible repo | `GET /repos/:owner/:repo/hooks` — check for a hook pointing at the gateway URL |
| **Slack** | Token is set (if configured) | Check env var presence |
| | Token authenticates | `POST auth.test` |
| **Deploys** | Recent deploy exists on both services | `GET /services/:id/deploys?limit=1` |
| | Deploy status is healthy | Check deploy status isn't `build_failed` or `deactivated` |

### Flags

| Flag | Effect |
|------|--------|
| `--json` | Output structured JSON instead of human-readable text (for CI) |
| `--fix` | Attempt to fix issues where possible (e.g., sync missing env vars from gateway to Workflows service) |
| `--local` | Check local dev prerequisites instead of production (Docker running, Postgres reachable, `.env` file exists, `render` CLI installed) |

## Implementation

### Package

A new `packages/cli/` package (or `scripts/cli/`) with two commands. Uses:

- Render API via `@renderinc/sdk` or raw `fetch` (the API is REST, no SDK needed)
- GitHub API via raw `fetch` (avoids adding `octokit` as a dependency)
- `readline` or `prompts` for interactive input
- Published as the `render-factory` bin in `package.json`

### Scope

| Task | Effort | Notes |
|------|--------|-------|
| CLI scaffold + arg parsing | Small | `commander` or plain arg parsing |
| `init` — Render auth + service discovery | Small | Render API calls |
| `init` — LLM key validation | Small | One HTTP call per provider |
| `init` — GitHub token validation | Small | GitHub API calls |
| `init` — env var sync to services | Small | Render API `update_environment_variables` |
| `init` — `.env` file writer | Small | Template from `.env.example` |
| `init` — interactive prompts + flow control | Medium | Happy path + error recovery |
| `doctor` — all checks | Medium | One function per check, parallel where possible |
| `doctor` — `--fix` mode | Small | Sync env vars, print webhook instructions |
| `doctor` — `--json` output | Small | Structured output alongside human-readable |
| Tests | Medium | Mock API responses, test each check independently |

**Total estimate:** ~3 days.

### Dependency on Render API

`init` and `doctor` rely on the Render API for service discovery and env var management. The commands work with a Render API key — they do not require the Render CLI. However, the Render CLI's `render workflows dev` is still needed for local development of the Workflows service.

If the Render API adds Workflows service creation, `init` can automate step 3 and eliminate the manual Dashboard step entirely.

---

## What this changes for a founder

**Before:** follow a 12-step setup guide across three dashboards, manually sync env vars between two services, hope you didn't miss anything, debug silent failures when something is wrong.

**After:**

```sh
# First time
npx render-factory init    # guided setup, ~5 minutes

# After any change, or when something breaks
npx render-factory doctor  # instant diagnostic
```

The factory still requires manual webhook creation on GitHub and manual Workflows service creation on Render — those are platform constraints, not things we can fix in code. But the CLI makes the steps explicit, validates each one, syncs what it can, and tells you exactly what to do for the rest.
